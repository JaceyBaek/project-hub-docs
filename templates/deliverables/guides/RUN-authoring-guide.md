## 2. ID 명명 규칙

- 알림: `{PROJECT}-RUN-A##` (Alert)
- 점검: `{PROJECT}-RUN-D##` (Daily/Periodic check)
- 복구: `{PROJECT}-RUN-R##` (Recovery)
- 번호: 2자리 zero-pad.

## 3. 섹션별 작성 규칙

### §1 서비스 개요 (REQ)
- 운영 담당자가 처음 봐도 파악할 수 있도록.
- 주요 컴포넌트 목록 / 배포 환경(리전·AZ) / 외부 의존 시스템 / 배포 방식 / SLA.
- ARC 산출물과 정합 (컴포넌트명 동일하게).

### §2 모니터링 / 알림 임계치 (REQ, ≥ 3건)
- 각 알림: ID / 메트릭 / 임계치 / 심각도 / 채널·담당.
- 심각도: Critical(즉시 대응) / Warning(확인 후 대응) / Info(참고).
- 채널: PagerDuty(Critical) / Slack 채널(Warning) 등 실제 도구명.
- 임계치는 정량 수치 필수 ("높으면 알람" 금지).

### §3 일상 점검 (REQ, ≥ 3건)
- 각 점검: ID / 항목 / 점검 방법(도구·경로) / 주기.
- 매일 점검 + 주간 점검 구분 권장.
- "확인한다" 수준이 아닌 구체적 도구·메뉴 경로까지.

### §4 장애 대응 플레이북 (REQ, ≥ 2개 시나리오)
- 각 시나리오: h3 제목(증상 설명) + 번호가 붙은 단계 목록.
- 단계마다 `data-chunk="step:{scenario}.{NN}"`.
- 단계 형식: `확인 → 원인 파악 → 조치 → 에스컬레이션 → 사후 처리`.
- 각 단계는 담당자가 직접 실행 가능한 수준으로 (명령어·경로 포함).
- OPM과의 차이: OPM은 일반 운영 절차, RUN은 장애 시 즉각 조치 플레이북.

### §5 복구 절차 / DR (REQ)
- **배포 롤백**: ECS/K8s 등 플랫폼별 구체적 단계.
- **DB 복구**: 백업 복원 절차 (Point-In-Time 등). RPO/RTO 수치 명시.
- **DR(재해복구)**: 전 리전 장애 시 Failover 절차 (해당 없으면 COND).
- 각 절차에서 "누가 승인해야 하는지" 명시.

### §6 에스컬레이션 / 연락처 (REQ)
- L1~L3 (또는 Vendor) 단계 정의.
- 각 단계: 역할 / 채널 / 에스컬레이션 기준 (시간 또는 조건).
- **실제 이름·전화번호는 `data-pii="name"` 마킹 또는 별도 내부 시스템 링크로 대체** (본 문서에 직접 기재 금지).

### §7 AI 메타데이터 (REQ)
- `primary_entities`에 컴포넌트명, 도구명, 장애 유형.
- `embedding_hints`: "어떤 서비스의 장애 대응·점검 절차" 1~2문장.

## 4. Trace 작성 원칙

- RUN 산출물은 상향 trace(REQ-N##)보다 **관련 문서 cross-reference**가 핵심.
- 플레이북 단계에서 CFG 설정 참조 시: `data-trace-up="CFG-###"`.
- 롤백 절차에서 ARC 컴포넌트 참조 시: `data-trace-up="ARC-NODE-##"`.
- 복구 절차 RTO/RPO 수치는 ARC 비기능 섹션 정합 확인.

## 5. 자가 점검 체크리스트

- [ ] `<meta>` 모두 채움
- [ ] 서비스 개요: 컴포넌트·환경·의존·SLA 모두 있음
- [ ] 알림 임계치 ≥ 3건, 정량 수치 포함

- [ ] 플레이북 ≥ 2개 시나리오, 각 ≥ 3단계
- [ ] 배포 롤백 절차 있음
- [ ] DB 복구 절차 있음 (RPO/RTO 수치)
- [ ] 에스컬레이션 L1~L3 정의, 기준 명시
- [ ] PII 필드 마킹 또는 외부 링크로 대체
- [ ] AI 메타데이터 모든 키 채움
- [ ] 검증표 전 행 PASS

## 6. 사용자에게 질문할 시그널

다음 정보가 없으면 추측 금지, 사용자에 질문:

- 배포 플랫폼 (ECS / K8s / VM / 서버리스)
- 모니터링 도구 (Grafana / Datadog / CloudWatch 등)
- 알림 채널 (PagerDuty / OpsGenie / Slack)
- 온콜 로테이션 구성 여부
- DR(재해복구) 요건 (Multi-region / 단일 AZ)
- RPO / RTO 목표치
- 에스컬레이션 연락처 관리 방식 (내부 시스템 링크)

## 7. 흔한 실수

| 실수 | 올바른 처리 |
|---|---|
| 플레이북이 "담당자에게 확인" 수준 | 구체적 명령어·메뉴 경로·도구 포함 |
| 알림 임계치가 정성적 (높으면) | "> 1% / 5분" 같은 정량 수치 |
| 에스컬레이션에 실명·전화번호 직접 기재 | data-pii 마킹 또는 내부 연락처 시스템 링크 |
| OPM과 내용 중복 | OPM = 일반 운영 절차, RUN = 장애 즉각 대응. 중복 부분은 OPM 참조로 대체 |
| DR이 "추후 작성" | 없으면 섹션 제거 + 이유 callout 표기 |
| 복구 절차에 승인자 없음 | DB 복구·인프라 변경은 승인 필요 명시 |

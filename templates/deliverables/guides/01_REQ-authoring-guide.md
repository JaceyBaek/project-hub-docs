# 요구사항정의서 (REQ) — AI 작성 가이드

> **이 문서의 독자는 AI 에이전트입니다.** 화면 사용자에게 노출되지 않습니다.
> 템플릿(`docs/01_plan/01_REQ_요구사항정의서.html`)을 복사해 실제 요구사항을 채울 때 반드시 이 가이드를 먼저 로드하십시오.

---

## 0. 작성 절차 (반드시 이 순서)

1. 템플릿 파일 복사 → `projects/<프로젝트>/docs/01_plan/01_REQ_<프로젝트명>_요구사항정의서_<YYYYMMDD>.html`
2. **head 의 `<title>` 변경** — `REQ · {시스템명} 요구사항정의서`
3. **메타바 6칸 채움** (담당자 / 버전 / 상태 / 수정일 / Epic / Confluence 경로)
4. **분류 태그 ≥ 3개** 채움 (#phase, #module, #domain 필수)
5. 본문 1~7장 작성 (아래 §3)
6. **AI 메타데이터 블록 (9장)** 갱신
7. **작성 완료 검증표 (10장)** 모든 행 PASS 처리
8. 변경 이력에 v0.1 행 추가
9. 자가 점검 (§5 체크리스트) 후 상태를 `Review`로

---

## 1. 필드 마커 의미

| 마커 | 의미 | 처리 |
|---|---|---|
| `REQ` | Required — 필수 | 누락 시 검증표 FAIL. 모르면 사용자에 질문. |
| `OPT` | Optional — 선택 | 해당 없으면 섹션 자체 제거 가능 (공란 금지) |
| `COND` | Conditional — 조건부 | 조건 충족 시에만 필수. 조건은 hint 주석 참고. |

> **금지:** "TBD", "미정", "추후 정의" 같은 placeholder 로 필수 필드를 채우지 말 것. 정보가 없으면 사용자에 물어볼 것.

---

## 2. ID 명명 규칙

- `REQ-B##` 비즈니스 요구사항
- `REQ-F##` 기능 요구사항
- `REQ-N##` 비기능 요구사항
- `REQ-C##` 제약/가정
- 숫자는 2자리 zero-pad (`REQ-F01`, `REQ-F12`)
- 한 번 부여된 ID는 **재사용/변경 금지**. 삭제 시 행을 남기고 "Deprecated" 표기.
- ID 누락은 검증표에서 자동 FAIL.

---

## 3. 섹션별 작성 규칙

### §1 개요 (REQ)
- **목적** — "왜 만드는가". 3문장 이내. KPI/비즈니스 지표 포함 권장.
- **범위 (In/Out)** — In-scope · Out-of-scope를 명시적으로 분리. 각 ≥ 2항목.
- **성공 기준** — 측정 가능한 수치만. "사용성 향상" 같은 모호어 금지.
- **§1-1 비즈니스 배경 (OPT)** — 해당 없을 시 통째로 제거.

### §2 용어 정의 (REQ)
- 도메인 용어 ≥ 5건.
- 본문에 처음 등장할 때 **굵게**.
- 영문/약어는 OPT (기술 용어는 가급적 병기).

### §3 이해관계자 / 페르소나 (REQ)
- 최소 2인.
- 각 페르소나에 **역할 / 목표 / Pain Point** 3요소 모두 필수.
- 시스템 관리자 페르소나는 OPT (운영 이슈가 명확할 때만).

### §4 비즈니스 요구사항 (REQ)
- ID `REQ-B##`, ≥ 3건.
- 중요도 (High/Medium/Low) 필수.
- Trace는 FLW/SCR/FUNC 중 ≥ 1개. 아직 없으면 빈 칸 (TRC Gap 분석에서 잡힘) — "TBD" 금지.

### §5 기능 요구사항 (REQ)
- ID `REQ-F##`, ≥ 5건.
- 설명 문형: **Given/When/Then** 또는 "사용자는 ~할 수 있다".
- 모호한 동사("관리한다", "지원한다") 단독 사용 금지 → 구체적 행동으로.

### §6 비기능 요구사항 (REQ)
- 4개 카테고리 **각 ≥ 1건** 필수: 성능 / 가용성 / 보안 / 호환성.
- 추가 카테고리 권장: 접근성, 운영성, 확장성.
- "기준" 칸은 **측정 가능한 수치**만 (95th percentile, 월간 가용성 % 등).
- "측정방법"은 도구·리포트명 명시 (APM 도구, QA 매트릭스 등).

### §7 제약/가정 (REQ)
- 제약(Constraint) ≥ 1건, 가정(Assumption) ≥ 1건.
- Risk는 OPT — 추가 시 완화 계획 함께.
- 제약 표현: "~만 가능" / "~ 사용 필수" 같은 한계.
- 가정 표현: "~로 전제한다" / "~될 것이다".

### §8 FAQ (COND)
- **실제 제기된 질문만** (이해관계자 인터뷰, 리뷰 코멘트 등).
- 가공 질문 / 일반 사용법 질문 금지 (그건 USM에 속함).
- 각 답에 관련 REQ ID 링크.
- 질문 0건이면 섹션 자체 제거.

### §9 AI 학습 메타데이터 (REQ)
필수 키:
```
doc_id              : 문서 고유 ID (메타바 일치)
version             : 메타바 일치
last_updated        : 메타바 일치
tags                : 페이지 상단 태그 일치
primary_entities    : 도메인 핵심 명사 (검색 키워드, 5~10개)
embedding_hints     : 문서 핵심 의미 1~2문장 (챗봇 청크 검색에 직결)
related_docs        : 하위 문서 prefix + 예상 개수
exclude_from_training : 민감정보 포함 시 true
chunk_strategy      : "heading-h2" 권장
```
- `embedding_hints` 품질이 낮으면 챗봇 hit rate가 급락. 키워드 나열 금지, 한 문장 요약으로.

### §10 작성 완료 검증표 (REQ)
- 14개 행 모두 PASS 마킹 후 승인 요청.
- 한 행이라도 FAIL이면 상태를 `Approved`로 변경 금지.
- 검증표 자체를 삭제하지 말 것.

---

## 4. Trace 작성 원칙

- Trace 칼럼은 "이 요구사항이 실현되는 곳"을 가리킴.
- 하향 추적: REQ → FLW → SCR → FUNC → UTC → ITS
- ID는 `id-chip` 컴포넌트로: `<span class="id-chip">FLW-001</span>`
- 한 REQ에 여러 trace 가능. 누락은 FAIL.

---

## 5. 작성 후 자가 점검 체크리스트

작성을 마치면 아래 모두 yes 확인:

- [ ] head `<title>` 이 시스템명 반영됐다
- [ ] 메타바 6칸 모두 실제 값 (TBD 없음)
- [ ] 태그 ≥ 3개
- [ ] §1 개요 3블록 모두 채움
- [ ] §2 Glossary ≥ 5건
- [ ] §3 페르소나 ≥ 2인, 3요소 모두
- [ ] §4 BR ≥ 3건, 중요도/Trace 있음
- [ ] §5 FR ≥ 5건, Given/When/Then 또는 "~할 수 있다"
- [ ] §6 NFR — 성능/가용성/보안/호환성 각 ≥ 1
- [ ] §7 제약/가정 각 ≥ 1
- [ ] §9 AI 메타데이터 모든 키 채움
- [ ] §10 검증표 모든 행 PASS
- [ ] 변경 이력에 본 작업 행 추가
- [ ] 모든 ID zero-pad, 중복 없음
- [ ] 화면 렌더링 시 가이드/주석이 노출되지 않음 (HTML 주석으로만 존재)

---

## 6. 사용자에게 질문해야 할 시그널

다음 정보가 없으면 **추측 금지**, 사용자에 질문:

- 시스템명 / Epic 코드 / 담당자
- 도메인 (HR/회계/물류 등)
- 성공 기준 수치 KPI
- 페르소나 (실 사용자 그룹)
- 비기능 요구 수치 (응답시간, 가용성, 보안 등급)
- 외부 연계 시스템 목록
- 법규/감사 제약 (보존기간, 암호화 등)

질문은 한 번에 모아서 (피크 5~7개), 답변 후 한 번에 작성.

---

## 7. 출력 후 메타데이터 갱신 트리거

다음 변경 시 §9 AI 메타데이터를 반드시 갱신:

- 새 요구사항 추가/삭제
- 도메인 키워드 변경
- 버전 bump
- 민감정보 추가 (`exclude_from_training: true`)

갱신하지 않으면 챗봇이 stale 응답을 낼 수 있음.

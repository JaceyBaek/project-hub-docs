4.장애 대응 플레이북

증상별 플레이북. 각 시나리오: 증상 → 원인 확인 → 조치 → 사후 처리. 최소 2개 시나리오.

4-1. API 5xx 오류율 급증

  1. 1) 확인 — Grafana 에러율 패널 → 특정 엔드포인트 집중 여부 확인
  2. 2) 로그 확인 — CloudWatch Logs → /ecs/approval-svc → ERROR 레벨 필터
  3. 3) DB 연결 확인 — RDS Metrics → DatabaseConnections, CPU 이상 시 §5 복구 절차 진행
  4. 4) 롤백 판단 — 최근 배포 이후 발생 시 §5 롤백 절차 즉시 실행
  5. 5) 에스컬레이션 — 15분 내 해결 불가 시 §6 에스컬레이션 경로에 따라 담당자 호출
  6. 6) 사후 처리 — 장애 종료 후 24시간 내 PIR(Post-Incident Review) 작성 → _manage/issues.md 등록

4-2. DB 응답 지연 / CPU 과부하

  1. 1) 확인 — RDS Metrics → CPU / ReadLatency / WriteLatency
  2. 2) 슬로우 쿼리 — RDS Performance Insights → Top SQL 확인
  3. 3) 긴급 쿼리 중단 — SELECT pg_cancel_backend(pid) 로 Long-running query 중단
  4. 4) 연결 수 확인 — SELECT count(*) FROM pg_stat_activity / 최대 연결 수 초과 시 앱 롤링 재시작
  5. 5) 스케일업 검토 — 근본 원인 쿼리 튜닝 전 임시 인스턴스 클래스 업그레이드 고려 (DBA 승인 필요)

4-3. HR 조직도 동기화 실패

  1. 1) 확인 — CloudWatch Logs → hr-sync 오류 메시지 확인
  2. 2) 영향 범위 — 당일 조직 변경 건수 확인 (HR 담당자 확인 요청)
  3. 3) 재실행 — Admin Console → 수동 동기화 트리거
  4. 4) HR 시스템 장애 시 — 이전 스냅샷 유지 + HR 시스템 복구 대기 + 담당자 알림

5.복구 절차 / DR

롤백 절차, DB 복구, DR(재해복구) 시나리오. RPO/RTO 수치는 ARC 정합.

5-1. 배포 롤백

  1. 1) ECS Console → approval-svc 서비스 → Update Service
  2. 2) Task Definition revision → 직전 안정 버전 선택 → Force New Deployment
  3. 3) Rolling Update 진행 확인 → 에러율 정상화 확인 (약 3~5분)

5-2. DB 복구 (Point-In-Time)

  1. 1) 복구 시점 결정 — 장애 발생 직전 시각 (RPO ≤ 1시간)
  2. 2) RDS Console → Restore to Point in Time → 신규 인스턴스로 복원
  3. 3) 앱 환경변수(DB_URL) 신규 인스턴스로 교체 → 롤링 재시작 (RTO ≤ 4시간)
  4. 4) 데이터 정합성 확인 후 구 인스턴스 삭제
DR 수행 전 필수
DB 복구 및 인프라 변경은 반드시 팀장 승인 후 진행. 야간·주말 장애 시 §6 에스컬레이션 경로로 즉시 보고.

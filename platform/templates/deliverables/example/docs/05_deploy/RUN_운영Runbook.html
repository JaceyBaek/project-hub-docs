§2 공통 진단 도구

모든 플레이북 실행 전 아래 명령으로 현재 시스템 상태를 파악합니다.

# 서비스 상태 전체 확인
sudo systemctl status attendance-api nginx postgresql redis

# 헬스체크 API
curl -s http://localhost:8000/health | python3 -m json.tool

# 최근 에러 로그 (100줄)
journalctl -u attendance-api --since "30 minutes ago" | grep -i error | tail -100

# 최근 경고 이상 로그 전체
journalctl -u attendance-api --since "1 hour ago" -p warning

# CPU/메모리 상태
top -bn1 | grep -E "attendance|postgres|redis"
free -h

# DB 연결 테스트
psql -h localhost -U attendance_user -d attendance_db -c "SELECT 1 AS alive;" 2>&1

# Redis 연결 테스트
redis-cli -h localhost ping

# 네트워크 포트 리스닝 확인
ss -tlnp | grep -E "8000|5432|6379|80|443"

# Nginx 에러 로그
tail -50 /var/log/nginx/error.log

§3 플레이북 상세

P2605991-RUN-P01 서비스 무응답 P1 Critical · 30분

의사결정 트리

📊
RUN-P01 의사결정 흐름
flowchart TD A[알람 수신] --> B{헬스체크 응답?} B -->|HTTP 200| C[일시적 오류 - 5분 모니터링] B -->|응답 없음| D{프로세스 확인} D -->|프로세스 없음| E[systemctl restart attendance-api] D -->|프로세스 있음| F{OOM 발생?} E --> G{복구됨?} F -->|Yes| H[메모리 확인 후 재시작] F -->|No| I[로그 분석 - 무한루프 등] G -->|Yes| J[완료 - 에러율 모니터링] G -->|No| K[에스컬레이션 - L2] H --> G I --> K

1단계 (0~5분): 상태 파악

1
헬스체크: curl -s http://localhost:8000/health → 응답 없으면 다음 단계
2
프로세스 확인: systemctl status attendance-api 및 ps aux | grep uvicorn
3
최근 에러 로그 확인: journalctl -u attendance-api --since "10 minutes ago" -p err

2단계 (5~20분): 복구 시도

A
케이스 A: 프로세스 없음
sudo systemctl restart attendance-api
재시작 후 5초 대기 → 헬스체크 재확인
B
케이스 B: OOM (메모리 부족)
free -h로 메모리 확인 → 불필요한 프로세스 종료 후 재시작
sudo systemctl restart attendance-api
C
케이스 C: 프로세스는 있으나 응답 없음
sudo systemctl stop attendance-api && sleep 3 && sudo systemctl start attendance-api

3단계: 복구 확인

✓
헬스체크 HTTP 200 확인
✓
에러율 1% 미만 확인 (Grafana 대시보드)
✓
로그에 신규 에러 없음 확인 (2분 모니터링)
🚨
20분 이내 복구 안 되면 즉시 L2 에스컬레이션 (슬랙 #it-oncall + 팀장 DM). 롤백 검토: OPM §4 롤백 절차
P2605991-RUN-P02 DB 연결 오류 P2 High · 1시간

1단계: DB 연결 상태 확인

1
DB 직접 연결 테스트: psql -h localhost -U attendance_user -d attendance_db -c "SELECT 1;"
2
PostgreSQL 프로세스 확인: sudo systemctl status postgresql
3
연결 풀 상태 확인: psql -c "SELECT count(*) FROM pg_stat_activity WHERE datname='attendance_db';"
4
DB 로그 확인: tail -50 /var/log/postgresql/postgresql-16-main.log

2단계: 복구 시도

A
케이스 A: PostgreSQL 프로세스 없음
sudo systemctl start postgresql → 연결 테스트 재확인
B
케이스 B: 연결 풀 고갈
API 서버 재시작으로 연결 풀 초기화: sudo systemctl restart attendance-api
C
케이스 C: DB_HOST 설정 오류
CFG §2 DB_HOST 값 확인 → 잘못된 경우 .env 수정 후 API 재시작

3단계: 복구 확인

✓
DB 연결 성공: psql ... -c "SELECT 1;" 응답 확인
✓
API 헬스체크에서 "db": "connected" 확인
✓
출퇴근 기록 API 정상 동작 확인 (test 요청)
P2605991-RUN-P03 Redis 연결 오류 P3 Medium · 30분

1단계: Redis 상태 확인

1
Redis ping 테스트: redis-cli -h localhost ping → PONG 확인
2
Redis 프로세스 상태: sudo systemctl status redis
3
메모리 사용량: redis-cli info memory | grep used_memory_human

2단계: 복구 시도

A
케이스 A: Redis 프로세스 없음
sudo systemctl start redis
B
케이스 B: 메모리 부족으로 maxmemory-policy eviction
redis-cli flushdb로 캐시 초기화 (JWT blacklist DB는 건드리지 않음)
주의: DB 1(JWT blacklist)은 redis-cli -n 1 flushdb 실행 금지
3
API 서버 재시작으로 Redis 연결 재설정
sudo systemctl restart attendance-api

3단계: 복구 확인

✓
Redis ping PONG 확인
✓
헬스체크 "redis": "connected" 확인
✓
응답 시간 정상화 확인 (캐시 miss로 일시적으로 느릴 수 있음 — 5분 이내 정상화)
⚠️
Redis 복구 직후 캐시 cold start로 응답 시간이 일시적으로 2~3배 느릴 수 있습니다. 5분 관찰 후 정상화 여부 확인하세요.

§2 서비스 시작 · 종료 · 상태 확인

서비스 시작

sudo systemctl start postgresql
sudo systemctl start redis
sudo systemctl start attendance-api
sudo systemctl start nginx

서비스 종료

sudo systemctl stop nginx
sudo systemctl stop attendance-api
# PostgreSQL, Redis는 API 서버 완전 종료 후 중지

상태 확인

# 서비스 상태
sudo systemctl status attendance-api
sudo systemctl status nginx

# 실시간 로그 (최근 5분)
journalctl -u attendance-api -f --since "5 minutes ago"

# 헬스체크 (HTTP 200 응답 확인)
curl -s http://localhost:8000/health | python3 -m json.tool

# 예상 응답
{
  "status": "healthy",
  "db": "connected",
  "redis": "connected",
  "version": "0.2.1"
}
⚠️
헬스체크 응답이 "status": "healthy"가 아닌 경우 즉시 Runbook P2605991-RUN-P01을 참조하세요.

§3 배포 절차 (Rolling Update)

ℹ️
Rolling 배포: 인스턴스 1개씩 교체하여 무중단 배포합니다. 배포 전 반드시 헬스체크 통과 확인 후 다음 인스턴스로 진행하세요.
# 1. 신규 버전 코드 pull
cd /opt/attendance && git fetch origin && git checkout v0.2.1

# 2. 의존성 갱신
source .venv/bin/activate
pip install -r requirements.txt --no-deps --upgrade

# 3. DB 마이그레이션 (다운타임 없는 마이그레이션만 허용)
alembic upgrade head

# 4. 인스턴스 1 재시작
sudo systemctl restart attendance-api@1

# 5. 인스턴스 1 헬스체크 (OK 확인 후 인스턴스 2 진행)
sleep 5 && curl -s http://localhost:8001/health | python3 -m json.tool

# 6. 인스턴스 2 재시작
sudo systemctl restart attendance-api@2

# 7. 최종 헬스체크
curl -s http://localhost:8000/health | python3 -m json.tool

배포 전 체크리스트

  • 통합 테스트 (ITS) 전체 통과 확인
  • DB 마이그레이션이 롤백 가능한지 확인 (alembic downgrade -1 테스트)
  • 스테이징 환경에서 동일 버전 검증 완료
  • 배포 담당자 2인 확인 (Four-eyes 원칙)

§4 롤백 절차

🚨
배포 후 에러율 5% 초과 또는 헬스체크 실패 시 즉시 롤백을 실행합니다. 판단 기준: 배포 후 5분 이내 확인.
# 1. 이전 버전으로 코드 복구
cd /opt/attendance && git checkout v0.2.0

# 2. DB 마이그레이션 롤백 (필요 시)
alembic downgrade -1

# 3. 서비스 재시작
sudo systemctl restart attendance-api

# 4. 헬스체크 및 에러율 확인
curl -s http://localhost:8000/health
journalctl -u attendance-api --since "5 minutes ago" | grep -i error | wc -l

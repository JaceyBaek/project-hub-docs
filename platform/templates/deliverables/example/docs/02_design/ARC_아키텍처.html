§1 개요

근태관리 시스템은 React 18 SPA 프론트엔드와 FastAPI 0.115.12 백엔드를 Nginx 리버스 프록시 뒤에 배치한 단순 2-tier 아키텍처입니다. 데이터 저장은 PostgreSQL 16, 세션/캐시는 Redis 7.2를 사용합니다. POC 단계이므로 단일 서버 배포이며, 운영 전환 시 HA 구성을 검토합니다.

  • 운영 환경: Ubuntu 22.04 LTS + systemd 서비스 관리
  • 배포 방식: 단일 서버 (POC), 이중화 미적용
  • 서비스 시간: 평일 06:00~22:00 (가용성 99.5% 목표)

§5 보안 아키텍처

JWT 인증 흐름

  1. 사용자가 POST /api/v1/auth/login으로 사내 SSO 또는 ID/PW 인증
  2. FastAPI가 JWT 액세스 토큰(8시간) + 리프레시 토큰(7일) 발급
  3. 이후 모든 API 요청 헤더에 Authorization: Bearer {token} 포함
  4. FastAPI 미들웨어가 JWT 서명 검증 + 블랙리스트(Redis) 체크
  5. 토큰 페이로드에서 employee_id, role 추출 → RBAC 적용

Nginx SSL Termination

  • Let's Encrypt TLS 1.2/1.3 (HTTP → HTTPS 리다이렉트)
  • HSTS 헤더 적용 (max-age=31536000)
  • 내부 FastAPI ↔ Redis ↔ PostgreSQL 통신은 localhost (비암호화)

CORS 정책

  • 허용 Origin: 사내 도메인만 (*.gsretail.internal)
  • 외부 Origin 요청 차단

§7 아키텍처 결정 기록 (ADR)

ADR-001
Redis 캐시 도입

컨텍스트: 근태 통계 조회(get_attendance_stats)는 복잡한 집계 쿼리를 포함하며, 동일 기간에 반복 호출됩니다. 요구사항에서 통계 조회 응답시간 3초 이내를 목표로 합니다.

결정: Redis를 인메모리 캐시로 도입. 통계 데이터 TTL 15분. 출퇴근 기록 시 관련 캐시 즉시 무효화.

결과: DB 쿼리 부하 감소, 응답시간 목표 달성 가능. 단, 캐시 무효화 타이밍 주의 필요. 캐시 장애 시 DB 직접 조회 폴백 구현 필수.

트레이드오프: 운영 복잡도 증가 (Redis 모니터링 필요). POC 단계에서는 단일 Redis 인스턴스로 충분.

ADR-002
FastAPI 선택 (Django/Flask 대비)

컨텍스트: 백엔드 프레임워크 선택. 팀은 Python에 익숙하며, API 문서 자동화와 비동기 처리가 요구됩니다.

결정: FastAPI 0.115.12 채택. Python 3.12 async/await 지원, Pydantic v2 타입 검증, OpenAPI 3.0 문서 자동 생성.

결과: 개발 속도 향상, 타입 안전성 확보, API 문서 자동 생성으로 프론트 협업 효율화.

트레이드오프: Django 대비 내장 기능(어드민, ORM) 적음. SQLAlchemy 2.0 별도 설정 필요. 팀 학습 비용 소요(1주 예상).

## 0. 작성 절차

1. 템플릿 복사 → `projects/<프로젝트>/docs/02_design/SEC_<프로젝트명>_보안설계서_<YYYYMMDD>.html`
2. `<meta>` 단일 소스 갱신 (project-id / doc-id / owner / tags / primary-entities)
3. `<title>` — `SEC · {시스템명} 보안설계서`
4. **§1 개요** — CIA 보안 목표, 적용 범위
5. **§2 위협 모델** — STRIDE 분류별 위협 + 대응 통제
6. **§3 인증/인가** — AuthN/AuthZ 설계
7. **§4 암호화** — 전송·저장 암호화 정책
8. **§5 입력 검증** — OWASP Top 10 기반 대응
9. **§6 감사 로깅** — 기록 대상·형식·보존
10. **§7 규정 준수** — 법령·정책 (해당 없으면 제거)
11. **AI 메타데이터(§8)** 갱신
12. **검증표(§9)** 자동 계산

## 2. ID 명명 규칙

- 위협: `{PROJECT}-SEC-T##` (Threat)
- 통제: `{PROJECT}-SEC-C##` (Control)
- 번호: 2자리 zero-pad. 삭제 시 행 유지 + "Deprecated".

## 3. 섹션별 작성 규칙

### §1 개요 / 보안 목표 (REQ)
- CIA 3요소 (기밀성·무결성·가용성) 각각 1문단.
- 적용 범위: 어느 레이어·컴포넌트까지 이 문서가 적용되는지. 외부 위임 (IdP, CDN 등)은 명시.

### §2 위협 모델 (REQ, ≥ 3건)
- STRIDE 6개 카테고리: Spoofing / Tampering / Repudiation / Information Disclosure / Denial of Service / Elevation of Privilege.
- 각 위협: ID / STRIDE 분류 / 위협 시나리오 / 대응 통제 / 위험도 (Critical/High/Medium/Low).
- trace-up: 비기능 요구사항 REQ-N## (보안 요구사항).
- 시스템 특성에 맞는 실제 위협만 선별. 형식적 나열 금지.

### §3 인증 / 인가 (REQ)
- **인증(AuthN)**: IdP / 토큰 방식 / 수명 / 갱신 정책.
- **인가(AuthZ)**: ROLE 기반 / ABAC / Scope 기반 중 선택. 리소스 소유자 확인 방식.
- 세션 관리 (Stateless JWT / Server-side Session).
- MFA 여부.

### §4 암호화 (REQ)
- 전송 구간: TLS 버전, 내부 서비스 간 mTLS 여부.
- 저장 데이터: DB 볼륨 암호화, 파일 스토어 암호화, 키 관리 (KMS / Vault).
- PII 마스킹: 어떤 필드가 PII이며 어떻게 처리하는지.

### §5 입력 검증 / 취약점 대응 (REQ, ≥ 3건)
- OWASP Top 10 기준 해당 프로젝트에 적용 가능한 항목 선별.
- 각 항목: ID / 위협 카테고리 / 구체적 대응 방법.
- "Parameterized Query 사용" 같은 구체적 방법을 명시. "SQL Injection 대응" 한 줄 금지.

### §6 감사 로깅 (REQ)
- 기록 대상 이벤트 목록 (인증 이벤트 / 권한 변경 / 중요 데이터 변경 등).
- 로그 형식 (JSON 필드 목록).
- 저장소 / 보존 기간 / PII 마스킹 방식.
- 조회 도구 / 접근 권한 (감사 로그는 읽기 전용 전용 계정만).

### §7 규정 준수 (COND — 해당 시 필수)
- 적용 법령 / 내부 정책 / 인증 목록.
- 해당 없는 경우 섹션 자체 제거 가능.

### §8 AI 메타데이터 (REQ)
- `primary_entities`에 STRIDE, 기술 방식, 주요 통제 수단.
- `exclude_from_training`: 내부 보안 상세가 민감하면 true 고려.

## 4. Trace 작성 원칙

- **위협 trace-up**: `data-trace-up="REQ-N##"` (보안 관련 비기능 요구사항).
- **통제 trace-up**: 해당 통제가 충족하는 위협 ID (`SEC-T##`).
- ARC의 보안 섹션과 정합 확인 — ARC-ID로 cross-reference 권장.

## 6. 사용자에게 질문할 시그널

다음 정보가 없으면 추측 금지, 사용자에 질문:

- 인증 방식 (OIDC IdP / API Key / 내부 LDAP)
- 개인정보 처리 여부 및 종류
- 법적 보존 요건 (법령명)
- DB 암호화 방식 (TDE / 컬럼 수준)
- 보안 점검 도구 (SAST / DAST / 취약점 스캐너)
- 감사 로그 보존 기간 요건
- MFA 적용 대상

## 7. 흔한 실수

| 실수 | 올바른 처리 |
|---|---|
| 위협 모델이 "일반론" 나열 | 시스템 컴포넌트·데이터 흐름 기반 실제 위협만 |
| 암호화 "AES 적용" 한 줄 | 전송/저장 구분 + 키 관리 방법 포함 |
| OWASP 대응이 "적용 예정" | 구체적 구현 방법 명시 |
| PII 마스킹 누락 | 개인정보 포함 필드마다 마스킹 처리 명시 |
| 감사 로그 "서버 로그 사용" | 이벤트 목록·형식·보존·조회 권한 별도 정의 |
| REQ-N과 미연결 | 보안 요구사항(REQ-N##)과 trace-up 필수 |
